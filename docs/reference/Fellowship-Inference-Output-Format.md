# Reading the model's answer from llama-cli / llama-mtmd-cli stdout on the tablets (answer boundary, prompt echo truncated at 500 characters)

Measured 2026-09-27 on real tablets by two probe orders (`probe-cli-output.20260927-192910`,
`probe-cli-multiline.20260927-193433`; full stdout and stderr in `tabfoundry-jobs\outbox`). Payloads cut the
answer at these boundaries and never by position ("first N characters", "first line", "after the last
prompt line").

## llama-cli (`-st --no-display-prompt`, tool / coding / chat payloads)

stdout, in order:

1. A loading spinner written with backspaces (`|\b-\b\\b/\b…`), the llama.cpp banner, and the command help
   block (`/exit`, `/regen`, `/clear`, `/read`, `/glob`).
2. `\n> ` followed by the prompt echo — despite `--no-display-prompt`.
   - Prompt of **500 characters or fewer**: the whole prompt, then `\n`.
   - Longer prompt: its **first 500 characters**, then ` ... (truncated)\n`. The model still receives the
     whole prompt; only the echo is cut.
3. The answer.
4. `\n\n[ Prompt: <n> t/s | Generation: <n> t/s ]`, then `\n\n\nExiting...\n`.

stderr is empty. Exactly one echo and one stats line per run.

## llama-mtmd-cli (vlm payloads)

stdout is the answer only (for example `"\n 42.\n\n\n"`). All logging — model load, image encoding, timings —
is on stderr. Read the whole stripped stdout; the answer may span several lines.

## The code

`Claude Home\phase5-prep\commission-artifacts\hard-bench\cli_answer.py` holds `llama_cli_answer(stdout,
prompt)` and `mtmd_answer(stdout)`, tested against the captured bytes (`test_cli_answer.py`). A payload runs as
one file on the tablet, so the generators copy these functions in (`payload_embed.py`) and check the copy
answers identically on the real captures. An unrecognised shape returns `answer_boundary:<reason>`: that row is
an instrument failure, kept out of pass rates and counted separately, and it carries `raw_stdout` for diagnosis.
Rows store the whole answer; nothing is truncated.

Payloads that use it: `map_swarm_code_hard*.py`, `map_tool_swarm_hard.py`, `map_vlm_swarm_hard.py` (all
generated). The frozen Phase 5 payloads (`map_swarm_code.py`, `map_tool_swarm.py`, `map_chat_swarm.py`,
`map_team_role.py`, `map_team_verify.py`, `map_vlm_swarm.py`) still store a fixed-length slice of the old
position-based read; their scoring parses the full text, but their stored answers are not reliable. Any new
payload derived from them goes through a generator that embeds `cli_answer`.

## Re-measure when

The llama.cpp runtime on the tablets changes (`runtime/` on rigby's store, or a node's `~/llm/llama-cli`).
Run the two probe payloads (`tabfoundry-jobs\payloads\probe_cli_output.py`, `probe_cli_multiline.py`, the
second generated by `gen_probe_multiline.py`) and re-run `test_cli_answer.py` against the new captures.
