# Lenovo tablet LineageOS flash — A-only families (X606F/X505F): the working procedure + the traps

This manual covers the flashing procedure for Lenovo tablets in the X606F and X505F families. These devices utilize A-only partitions and are flashed from a Windows host.

For the gandalf-class (TB-X6C6F), which utilizes A/B slots with logical partitions within `super`, see [[FLASH-NEW-TABLET-gandalf-class-X6C6F-from-rigby]].

## Pre-flash checks

Before initiating the unlock process, verify that `sys.oem_unlock_allowed` is set to 1. If this property is not 1, the unlock operation will fail with "Unlock operation is not allowed." Checking this value before attempting the unlock ensures any refusal is unambiguous.

## Driver configuration (Windows)

Ensure the correct registry values are present for fastboot detection. A missing registry value can cause `fastboot devices` to return empty results even after a successful driver bind. See §5a of the original source text for the specific registry fix.

## Flash execution sequence

1. Erase the system partition: `fastboot erase system`
2. Flash the system image: `fastboot flash system`
   - These commands target physical partitions appropriate for A-only devices.
3. Recovery mode entry:
   - Use the correct key combination and timing.
   - Release keys at the appearance of the logo, not after it has fully loaded.

## Post-flash provisioning

Provision the device to Fellowship parity standards as defined in §8 of the original source text.

## Common failure modes

- **ffmpeg runtime error:** The `libc++` library trap may result in ffmpeg being installed with the correct version but failing to run. See §8a of the original source text for resolution.

## Flash disabled vbmeta to prevent GSI bootloops

Every GSI deployment for both device families requires flashing a disabled `vbmeta` partition before any boot operations. Failure to execute this step results in a bootloop on every unit.

```bash
fastboot --disable-verity --disable-verification flash vbmeta vbmeta.img
```

**Design doctrine:**
The `vbmeta` partition carries a hashtree descriptor for the `system` partition. Generic System Images (GSI) do not match stock hashes. If dm-verity is configured, mount attempts fail and cause a bootloop.

This failure occurs independently of the bootloader’s security state (`secure: no`). Even with an unlocked bootloader (`unlocked: yes / secure: no`), AVB enforcement can persist. Assuming AVB is disabled solely because the bootloader is unlocked is incorrect.

### Generating a disabled vbmeta image
The Fellowship flash procedure does not require XDA, LMSA, or external firmware mirrors. It uses an empty `vbmeta` image generated by Google's `avbtool` from AOSP.

**Verification:** Run `avbtool info_image --image vbmeta_disabled.img`; output must show `Flags: 3`.

The canonical copy of `vbmeta_disabled.img` (and `avbtool.py`) is stored durably at `E:\SSDShared\Lab\fellowship\avb\`.

## Fastboot-only LineageOS flashing procedure (No TWRP)

Use this fastboot-only sequence for X606X, X606V, and X606F devices. Do not use TWRP.

```bash
fastboot erase system
fastboot erase userdata
fastboot erase cache
fastboot --disable-verity --disable-verification flash vbmeta vbmeta_disabled.img
fastboot flash system <gsi>.img
fastboot -w
fastboot reboot
```

### First boot timing

The first boot requires 5–10 minutes. Do not intervene or judge failure before this window expires.

### `fastboot -w` behavior on these devices

On X606 series devices, `fastboot -w` does not format the `userdata` partition. It formats `cache` and prints:

```
Erase successful, but not automatically formatting / File system type raw data not supported
```

This message refers to the **metadata** partition (`partition-type: raw data`).

If genuine `userdata` formatting is required, run:

```bash
fastboot format:ext4 userdata
```

A successful format of a 23.4 GB `userdata` partition results in 188 inode groups. Formatting `cache` via `-w` results in 2 inode groups.

**Note:** vbmeta configuration, not userdata formatting state, is the cause of boot loops.

### Root Access and Provisioning

Termux `su` is non-functional on all nodes. The PHH superuser binary included in `_bvS` images is not reachable from the Termux uid. The string "No su program found on this device" returned by `su -c id` is a Termux stub response and does not indicate root availability.

Do not use `su` over SSH for provisioning.

Use `adb root` for privileged access. These are `-userdebug` builds with `ro.debuggable=1`. Note that `adb root` restarts adbd, which terminates any processes launched from an existing adb shell.

To enable persistent TCP debugging:
1. Obtain root via `adb root`.
2. Run `setprop persist.adb.tcp.port 5555`.
3. Reboot the node.

The `persist.adb.tcp.port` property persists across reboots after being set via `adb root`. Nodes do not require pairing for TCP access on port 5555 once configured.

Full provisioning procedure: see [[Fellowship-Node-Provisioning]] §<heading>.

## UNLOCK commands by chipset

Unlock commands differ by SoC. They are not interchangeable.

### MediaTek (X606F, X6C6F)
*   **Command:** `fastboot flashing unlock`
*   **Response:** OKAY in 7–21 s. Device stays in fastboot mode.
*   **Input required:** **Physical Volume Up confirmation on the tablet.** the owner directly confirms
    he performed this during every prior tablet intake. Older journal text saying no button was
    needed is incorrect; the canonical intake runner must pause, tell the operator to watch the
    unlock screen, and issue the command only when the operator is ready to press Volume Up.
*   **Verification:** Immediate post-command state check.

### Qualcomm (X505F)
*   **Command:** `fastboot oem unlock-go`
    *   Note: `fastboot flashing unlock` fails with `remote: 'Need wipe userdata. Do 'fastboot oem unlock-go''`.
*   **Response:** OKAY in <0.2 s. Device disconnects from USB, wipes userdata, and boots into fresh Android.
*   **Verification:** A follow-up `getvar` blocks until timeout; this is expected behavior during wipe, not failure.

### Post-unlock constraints
1.  Unlocking wipes userdata.
2.  USB debugging is disabled after wipe.
3.  `adb reboot bootloader` ceases to work after disablement.
4.  Re-enter fastboot mode using **Vol Down + Power** (functional from setup wizard).
5.  WINUSB binding survives the wipe process, but bindings are per-OS-install; see §5 for device-specific persistence rules.

### 4a. `FAILED (remote: 'Unlock operation is not allowed')` — precondition check

The unlock command requires `sys.oem_unlock_allowed=1`. If this property is `0`, the bootloader begins the unlock flow, waits approximately 291 seconds, then fails with:

```
(bootloader) Start unlock flow
    ... ~291 s of nothing ...
FAILED (remote: 'Unlock operation is not allowed')
```

**Check this precondition BEFORE initiating unlock:**
```bash
adb -s <SERIAL> shell getprop sys.oem_unlock_allowed     # 1 = will unlock, 0 = will refuse
```

**Fix procedure (Android UI):**
The flag is bootloader-side and cannot be baked into images. To enable it:
1. Boot to Android and complete the setup wizard.
2. Connect to WiFi (*OEM unlocking* remains disabled until Google services are reachable).
3. Settings → About tablet → tap **Build number** seven times.
4. Developer options → Enable **OEM unlocking** (and **USB debugging**).

With the flag set, `fastboot oem unlock` completes in the standard MediaTek timing band (7–21 s) and returns OKAY.

**Fallback (if UI is blocked):**
If OEM unlocking is greyed out or policy-blocked (e.g., MDM, FRP), the alternative is MediaTek BROM mode via `mtkclient` or SP Flash Tool. This interfaces below the bootloader. Support for MT6765 exists but is **unverified on these units** and carries preloader-brick risk. Do not use this path while the two-minute UI toggle is available.

### 4b. ⭐ RECOVERY MODE (the Chinese-text menu) — button combo + TIMING, now VERIFIED

**Verified by the owner on 2026-08-12 on HA197X4L; he wiped the device with it.** Until then this combo
existed in the library only as an XDA research note restated twice, with **no record of anyone
actually entering recovery** — the one person who had ever done it was the owner, and how was never
written down. He was right to distrust it when it was quoted back at him.

```
Vol Down + Power              = fastboot
Vol Up + Vol Down + Power     = recovery   (the bluish-white Chinese-text menu)
```

⚠ **THE TIMING IS THE WHOLE TRICK, AND IT IS THE OPPOSITE OF THE INSTINCT.**
**Release all three the moment the Lenovo logo appears.** Holding *through* the logo — which feels
like the safe thing to do, and which a session confidently advised — drops the device into a normal
boot every time. Sequence:
1. Power off **completely** (hold Power ~10 s). Charge first; the guides specify >86%.
2. Press **Vol Up + Vol Down + Power** together.
3. **Let go of all three at the logo.** Recovery appears a few seconds *after* you release.

**Two different screens, two different navigation schemes** — the library previously conflated them:
* **MediaTek boot menu** — prints its own hint, `[VOLUME_UP to select. VOLUME_DOWN is OK.]`, i.e.
  Vol Up *moves*, Vol Down *confirms*. Entries: 恢复模式 Recovery · 快速启动 Fastboot · 正常启动 Normal.
* **Android recovery** — standard AOSP: Volume moves, **Power confirms**. Entries include
  清除数据 / 恢复出厂设置 wipe-data/factory-reset · 更新系统（通过 ADB）apply update from ADB ·
  立即重启系统 reboot system now · 关机 power off.
**Read the hint the screen prints and trust it over any doc, including this one.**

⚠ **"Apply update via ADB" is a dead end for our purposes.** It puts the device in **sideload** mode:
the devnode flips to `VID_18D1&PID_D001` and `adb devices` reports `unauthorized`. That is normal for
sideload and not a fault, but sideload only accepts a signed update package. Back out with
立即重启系统.

⚠ **A recovery wipe does not advance the flash on its own** — it neither unlocks the bootloader nor
sets `sys.oem_unlock_allowed`, and the flash procedure wipes anyway. Its real value is clearing a
previous owner's account/MDM. And **a locked bootloader refuses `erase`/`flash`**, so recovery is the
*only* wipe route available before unlock.

## 5. DRIVER BIND: PER DEVICE (SERIAL), NOT PER HOST

Fastboot mode reports protocol ID `Prot_03`. The system lacks an INF match for this protocol, causing tablets to enumerate as classless with `ConfigFlags=0x40` and fail with **Error Code 28**.

Because the driver bind is stored on the DEVNODE and keyed by serial number, each tablet requires individual binding. Adding a new tablet to a host where other tablets are already bound still results in Error Code 28 until that specific device is bound.

### Procedure

1. Open **Device Manager**.
2. Use the driver picker (`DIF_SELECTDEVICE`) to install the selected driver node for the device.
   - This method skips hardware-ID matching and binds the driver directly.
3. Repeat for every new tablet added to any host.

> Note: `winusb.inf` matches `USB\Class_ff&SubClass_42&Prot_01` (**ADB**), not Fastboot.

### `fastboot devices` EMPTY after successful WinUSB bind

#### Symptom and Cause
Device Manager shows a healthy status (`Status: OK`, `CM_PROB_NONE`) with `WinUSB` as the service, but `fastboot devices` returns empty and `fastboot getvar` hangs on `< waiting for any device >`. The cause is that Device Manager installed the generic inbox WinUSB node (`DriverDesc = WinUsb Device`). The generic `winusb.inf` does not write `DeviceInterfaceGUIDs`, so the device publishes no interface. `fastboot.exe` enumerates devices via `GUID_DEVINTERFACE_ANDROID_USB` (`{F72FE0D4-CBCB-407d-8814-9ED673D0DD6B}`); without this GUID in the registry, the device is invisible to fastboot.

#### Diagnosis
Compare the devnode’s registry keys against a working sibling. A working node (bound via Android INF) contains `DeviceInterfaceGUIDs`. A broken node (bound via generic picker) lacks this key.

```powershell
reg query "HKLM\SYSTEM\CurrentControlSet\Enum\USB\VID_0E8D&PID_201C\<SERIAL>\Device Parameters"
```
*   **Working:** Contains `DeviceInterfaceGUIDs` with value `{F72FE0D4-CBCB-407d-8814-9ED673D0DD6B}`.
*   **Broken:** Contains only `EnumerationRetryCount` and `SymbolicName`.

#### Fix
Write the missing GUID and restart the devnode. Requires SYSTEM privileges (see [[RUNBOOK-Elevation-and-Headless-Tasks]]).

```powershell
$key = "HKLM:\SYSTEM\CurrentControlSet\Enum\USB\VID_0E8D&PID_201C\<SERIAL>\Device Parameters"
New-ItemProperty -Path $key -Name DeviceInterfaceGUIDs -PropertyType MultiString `
  -Value @('{F72FE0D4-CBCB-407d-8814-9ED673D0DD6B}') -Force
pnputil /restart-device "USB\VID_0E8D&PID_201C\<SERIAL>"
```
The restart is required to publish the interface. See `bind_fastboot_guid.ps1` for automation.

#### Distinctions and Constraints
*   **Not a driver installation failure:** This issue affects already-bound drivers. It differs from dead ends involving mismatched hardware IDs during installation attempts.
*   **fastbootd VID/PID:** Devices entering fastboot mode via `fastboot reboot fastboot` present a different USB ID (`VID_18D1&PID_4EE0`). This ID requires its own bind configuration. Relevant only for A/B dynamic-partition devices (e.g., HA1WKD37).
*   **Contraindicated actions:**
    *   Do not retry `SetupDiSetSelectedDriver`/`DiInstallDevice` (`ERROR_CLASS_MISMATCH`), `UpdateDriverForPlugAndPlayDevices` (no matching hardware ID), injecting `USB\MS_COMP_WINUSB` into CompatibleIDs (wiped on restart), or reusing OEM Android INFs (none name these IDs).
    *   Do not disable driver signature enforcement or enable test-signing. This is a machine-wide security setting on the Hyper-V + Plex host and is out of bounds.

## X606F WiFi Association Failures (Error Code 31)

The Lenovo TB-X606F tablet (`achilles6`) fails to associate with the GSI access point. The `wpa_supplicant` log reports `CTRL-EVENT-ASSOC-REJECT status_code=31`, indicating a Robust Management Frame (802.11w/MFP) policy violation.

Other devices (X6C6F, X505F) associate successfully on the same AP and configuration. The failure is specific to the MediaTek WiFi driver in the X606F hardware when running Android 12+ frameworks that enable WPA3 auto-upgrade.

### Root Cause
The Android 12+ framework enables `config_wifiSaeUpgradeEnabled` by default, which automatically upgrades PSK connections to SAE (WPA3). The AP operates in WPA2/WPA3 transition mode. When the X606F attempts this auto-upgrade, its legacy MediaTek driver fails to complete MFP negotiation, resulting in rejection.

### Resolution
Deploy LineageOS 18.1 (Android 11) GSI images to all X606F devices. Android 11 does not perform automatic WPA3 upgrades, avoiding the driver incompatibility.

**Image Source:** `andyyan-gsi/lineage-18.x/`
**Filename:** `lineage-18.1-20240121-UNOFFICIAL-arm64_bvS.img.xz`

### Exhausted Config-Level Fixes
The following interventions were tested and failed to resolve the issue. Do not retry:

| Intervention | Result |
|---|---|
| Force WPA2 via `connect-network … wpa2` | Reject 31 (auto-upgrade still triggered) |
| Force WPA3 via `connect-network … wpa3` | Reject 31 |
| Strip SAE block from `WifiConfigStore.xml` | Framework regenerates the block on boot |
| Pin frequency band (`-b <bssid>`) | No change; rules out band-specific issues |
| Check for WiFi/SAE overlays (`cmd overlay list`) | None exist |
| Check device config SAE/PMF flags | None exposed |
| Phh Treble app SharedPreferences | Only unrelated keys present |
| Direct `wpa_cli` control | Framework owns the control socket |

### Configuration Notes
- On Android 12+, `WifiConfigStore.xml` is located at `/data/misc/apexdata/com.android.wifi/`. The legacy path `/data/misc/wifi/` is unused.
- AP-side configuration changes are ruled out per design directive.

### USB provisioning: persist.adb.tcp.port=5555

Configure persistent ADB over TCP while the device is connected via USB. This configuration ensures `adbd` listens on port 5555 at every boot, eliminating the need for physical pairing codes or manual re-enablement after reboot.

```bash
adb -s <serial> root                                   # -userdebug GSI, so this works
adb -s <serial> shell 'setprop persist.adb.tcp.port 5555'
adb -s <serial> shell getprop persist.adb.tcp.port     # MUST read back 5555
```

**Prerequisite:** `persist.*` properties require root access. Non-root shells (uid 2000) will fail with "Failed to set property". The command `adb -s <serial> root` restarts `adbd`; the daemon comes back online listening on port 5555.

**Design constraint:** Do not use wireless debugging (`adb_wifi_enabled=1`) for permanent access. Wireless debugging uses a random per-session port and does not re-arm TLS at boot on these GSIs. Nodes configured with wireless debugging are unreachable by `adb` after reboot.

This configuration must be completed before subsequent steps (doze whitelist, starting `wifi_watchdog`, diagnostics, or reboot testing), as all downstream procedures require an active ADB connection.

### `termux-wake-lock` and Node Stability Requirements

Hold `termux-wake-lock` on every node before sustained work (apt installs, downloads). Android deep doze suspends CPU and radio under sustained load, causing LAN disconnection (no ARP/ping) and SSH drops. Doze whitelisting (`dumpsys deviceidle whitelist +com.termux`) does not substitute for an explicit wake lock.

```bash
adb -s <target> shell "run-as com.termux sh -c 'export PREFIX=/data/data/com.termux/files/usr HOME=/data/data/com.termux/files/home PATH=$PREFIX/bin:$PATH; termux-wake-lock'"
```

#### Verification
`termux-wake-lock` returns exit code 0 regardless of success. Verify via `dumpsys power`:
1. Confirm a `PARTIAL_WAKE_LOCK` naming termux exists.
2. Check lock count: `Locks acquired: N / released: M` means `N-M` locks are held. A count of `acquired: 1 / released: 0` means one lock is held.

#### Provisioning Script Behavior
`provision_node.sh` acquires and verifies the wake lock before running apt. It aborts if the lock cannot be acquired.

#### Required Node Components
The following components are load-bearing and non-optional:

| component | requirement |
|---|---|
| **`com.termux.boot`** | Termux does not self-launch after reboot. `Termux:Boot` must be launched once to register for `BOOT_COMPLETED`. Without it, sshd fails to restart post-reboot. |
| **APKs from a live node** | `Termux:Boot` requires the same signing key as Termux. Fresh downloads from F-Droid may mismatch keys, causing boot scripts to fail silently. Pull APKs from an existing running node. |
| **ffmpeg** | Required by `hwdec.json`'s `input_cmd`. Provisions successfully without it but decodes nothing. |
| **doze whitelist** | Added via `adb shell dumpsys deviceidle whitelist +com.termux`. Verify via adb; the Termux uid cannot read `dumpsys deviceidle`, so internal checks return empty results even when whitelisted. Neither substitutes for `termux-wake-lock`. |
| **`.fellow_name` / `.fellow_token`** | Name is per-node. Token is a shared fellowship secret (`fellow_ensure_token` mints once). Copy the existing token; do not mint a new one. |

### `libc++` Skew Breaks ffmpeg: Diagnosis and Remediation

If `apt install ffmpeg` leaves dpkg state as **`iF`** (installed, failed-config) with the error:
```
CANNOT LINK EXECUTABLE ".../bin/ffmpeg": cannot locate symbol
"_ZNSt6__ndk127__from_chars_floating_point..." referenced by "libplacebo.so"
```
The node likely has **`libc++ 27c`** while `libplacebo` requires **29**. The bootstrap image may not force the dependency upgrade.

Remediation:
```bash
apt-get install -y libc++ && dpkg --configure -a
```

Verification: 
1. Check package status with `dpkg -l ffmpeg` (must show `ii`).
2. Execute the binary to confirm linkage and output: `ffmpeg -version`.

**Design Doctrine: Existence Is Not Function.** 
Provisioning checks that verify file presence (`test -x`) are insufficient for runtime readiness. A binary may exist but fail to link or execute. All provisioning validations must include a functional test that executes the component and reads its output to confirm operational capability.

### 8b. Positive control procedure: agent self-test

The positive control for object detection uses the agent’s own self-test, not a hand-rolled image.

**Procedure**
1. Run: `python ~/tablet_foundry.py --detect-selftest`
   - This invokes `detect_selftest()`, labeled "THE LIVE DECOY".
2. Expected output: `"ok": true` with label `dog` and confidence ~0.992.
3. Verify bounding box identity between nodes:
   - The bounding box returned by the test node must be identical to that of the reference node (`sam`).

- This command reads raw frames from stdin; it does not accept an image path argument.
- **Verification rule:** A control that fails on a known-good node indicates a defect in the instrument or method, not the subject. Always validate new checks against a working node before attributing failure to the target system.
