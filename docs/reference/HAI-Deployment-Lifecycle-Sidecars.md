# HAI Orchestrator - Deployment Lifecycle & Sidecars



## Self-deploy state machine (`hostops_deploy.py`, broker)
- Endpoints: `POST /deploy/start {workspace,user}`, `GET /deploy/status`, `POST /deploy/promote {job}`, `POST /deploy/cancel`. From orchestrator: `hostops._request("POST","/deploy/start",json_body=…)` etc. (or the `self_deploy`/`deploy_promote` tools, which wrap these behind confirm cards).
- **Canary-first flow:** `preflight` (diff workspace vs canonical) → `backup` (snapshot canonical → `/opt/arrstack/deploy-backups/<job>`) → `promote` (copy changed top-level `*.py` + `tests/*.py` into canonical) → `canary_build` + `up` `orchestrator-canary` on **:8101** → `canary_verify` (`/health` + `/modes` smoke; **LIVE untouched**) → **`awaiting_promote` (human gate)** → `cutover` (rebuild+recreate live orchestrator) → `live_verify` (`/health`; **auto-rollback** to backup on failure) → `cleanup` (remove canary) → `done`.
- Build/up run via one-off `docker:cli` so the compose files stay the source of truth. Canary = a `profiles:[canary]` service inheriting live via a YAML anchor. Promotes **only top-level `*.py` + `tests/*.py`** (compose/secrets protected). `coding-runner` is a **separate** rebuild (its nested source must be synced to canonical after a rollout).

## Coding-runner deploy path (separate from the orchestrator self-deploy — NO canary)
The `coding-runner` sidecar is a **separate build/deploy from the orchestrator** (the canary-first self-deploy broker promotes ONLY top-level orchestrator `*.py` + `tests/*.py`, never coding-runner).
- **Canonical source:** `/opt/arrstack/orchestrator/coding-runner/` (compose `build: ./orchestrator/coding-runner`). NOT `/opt/arrstack/coding-runner/` (that's only `backups/`).
- **State + workspaces are HOST-MOUNTED → preserved across rebuilds:** `/opt/arrstack/coding-state:/state` (tasks/decisions/projects/checkpoints) and `/opt/arrstack/coding-workspaces:/app/workspaces` (so editing `orchestrator-real` "inside the container" actually writes the host dir). A rebuild swaps only code; durable state survives.
- **Deploy = direct, no canary/auto-rollback:** edit canonical source → `cd /opt/arrstack && docker compose build coding-runner && docker compose up -d coding-runner` → verify (`GET :8100` health, `/tasks`). **Fallback is manual:** back up the source first, verify exhaustively after, revert source + rebuild on any failure. Because there's no canary, treat coding-runner deploys more cautiously than orchestrator ones (build+test+stage for a supervised deploy unless confident).
